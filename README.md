### 2. Обоснование выбора суррогатных и составных ключей

Для основных сущностей используются суррогатные первичные ключи типа `BIGINT GENERATED ALWAYS AS IDENTITY`:

* `users.user_id`;
* `sources.source_id`;
* `categories.category_id`;
* `tags.tag_id`;
* `news.news_id`;
* `favorites.favorite_id`;
* `subscriptions.subscription_id`.

Такой подход позволяет отделить техническую идентификацию записи от её бизнес-атрибутов.

Например, электронная почта пользователя может измениться, поэтому `email` не используется в качестве первичного ключа. При этом уникальность электронной почты сохраняется с помощью ограничения `UNIQUE`.

Аналогично, название источника, его URL, название категории или тега могут изменяться. Поэтому они не используются как первичные ключи. Для новости также не используется её заголовок или внешняя ссылка, поскольку эти данные относятся к содержимому новости и не являются стабильным идентификатором записи.

Суррогатный ключ `news_id` позволяет однозначно идентифицировать новость независимо от её заголовка, URL и других изменяемых атрибутов.

Для таблиц `news_categories` и `news_tags` используется составной первичный ключ:

* `(news_id, category_id)`;
* `(news_id, tag_id)`.

Он однозначно идентифицирует саму связь между двумя сущностями и не требует отдельного технического идентификатора.

Для таблицы `favorites` дополнительно используется ограничение `UNIQUE(user_id, news_id)`. Оно отражает бизнес-правило: один пользователь не должен добавлять одну и ту же новость в избранное несколько раз.

Таким образом, суррогатные ключи используются для самостоятельных сущностей, а составные ключи — для таблиц, представляющих связи между сущностями.

### 3. Матрица «таблица → владелец данных → бизнес-сценарий»

| Таблица           | Владелец / ответственный     | Связанный бизнес-сценарий                                                             |
| ----------------- | ---------------------------- | ------------------------------------------------------------------------------------- |
| `users`           | Пользователь / Администратор | Управление учётными записями и доступом                                               |
| `sources`         | Редактор / Администратор     | Сценарий 5 «Добавление нового источника»                                              |
| `news`            | Система / Редактор           | Сценарий 1 «Просмотр новостной ленты»; Сценарий 6 «Модерация импортированной новости» |
| `categories`      | Редактор                     | Сценарий 6 «Модерация импортированной новости»                                        |
| `tags`            | Редактор                     | Сценарий 6 «Модерация импортированной новости»                                        |
| `news_categories` | Система / Редактор           | Сценарий 6 «Модерация импортированной новости»                                        |
| `news_tags`       | Система / Редактор           | Сценарий 6 «Модерация импортированной новости»                                        |
| `subscriptions`   | Пользователь                 | Сценарий 4 «Подписка на тему или источник»                                            |
| `favorites`       | Пользователь                 | Сохранение новости в избранное                                                        |

Распределение основано на ролях и сценариях, определённых в первой лабораторной. В частности, пользователь может подписываться на темы и источники и сохранять новости в избранное; редактор работает с источниками, категориями, тегами и импортированными новостями; администратор отвечает за учётные записи, роли и системные параметры.

Сценарии 4, 5 и 6 непосредственно описаны в первой лабораторной как подписка пользователя, добавление нового источника редактором и модерация импортированных новостей соответственно.
